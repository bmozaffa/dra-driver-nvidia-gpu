Kubernetes can schedule based on the count, but it knows very little about *which* device gets used or any detailed configuration.\n- With **DRA**, the resource is handled through dedicated Kubernetes APIs like **`ResourceClaim`**, **`ResourceClass`**, and **`ResourceSlice`**. That lets a driver describe devices in much richer ways and lets workloads request resources with more structure and policy.\n\nThe practical difference is:\n\n- **Extended resources are simple integers**: good for “I need one GPU.”\n- **DRA is claim-based and driver-managed**: better for “I need a GPU with these attributes, this sharing mode, this topology, and this runtime preparation.”\n\nA useful way to think about it:\n\n- **Extended resources** = “book me one seat.”\n- **DRA** = “reserve a specific kind of seat, with constraints, and prepare it before I arrive.”\n\nWhy DRA exists:\n\n- Many devices are not interchangeable.\n- Allocation may need extra logic beyond counting.\n- The kubelet may need a **prepare/unprepare** step before a container can actually use the device.\n- Vendors may need to expose capabilities, topology, sharing behavior, or configuration safely through Kubernetes objects.\n\nCompared with legacy extended resources, DRA gives you:\n\n- **Richer selection** of devices and capabilities\n- **Structured allocation objects** instead of only Pod resource requests\n- **Per-claim lifecycle** rather than only per-Pod integer accounting\n- **Driver-controlled preparation** on the node before container startup\n- Better support for advanced hardware scenarios like partitioning, topology-aware assignment, and nontrivial setup\n\nWhat does **not** change:\n\n- Kubernetes still schedules workloads onto nodes.\n- A vendor-specific component still integrates hardware with Kubernetes.\n- Users still ask for specialized resources in manifests.\n\nBut the integration model changes from:\n\n- **Legacy**: “node advertises counts, Pod consumes counts”\n\nto:\n\n- **DRA**: “driver publishes resource information, workload creates or references claims, scheduler allocates, kubelet prepares, then the container uses the prepared resource”\n\nIf you want, I can also give you:\n- a **Pod/claim YAML example**, or\n- a
